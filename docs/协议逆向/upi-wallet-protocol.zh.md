# UPI 钱包通用协议逆向分析：从 OTP 登录到流水查询的接口模型

> 本文为一次**授权**的安卓逆向研究记录，针对印度主流 UPI 钱包类 App 的客户端通信协议。文中的 App 名称仅用于说明平台差异，所有端点、账号、敏感参数均已脱敏；讨论仅限于接口模型、加密机制与安全防护层面的技术分析，不包含任何可复用的攻击代码，也不针对任何真实账户或服务。

**覆盖平台：** Amazon Pay、MobiKwik、PhonePe、BharatPe Business、Airtel、FreeCharge、Paytm
**研究目的：** 抽象此类 UPI 钱包 App 在 **OTP 登录、查询 UPI ID（VPA）、查询流水** 三类核心功能上的接口模型、参数规范、加密机制及安全措施，便于安全研究、风控建模与合规审计。

---

## 一、总体架构概述

### 1.1 通信协议

所有平台均采用 **HTTPS（TLS）**，部分平台启用 **HTTP/2** 以降低握手开销。请求体以 **JSON** 为主流格式；少数旧接口（如 Amazon Pay）仍保留 **HTML 页面渲染 + 客户端解析** 的传统模式。

### 1.2 整体会话生命周期

UPI 钱包的完整会话遵循一条清晰的线性链路，且**强状态依赖**——每一步的输出都是下一步的输入：

```
设备初始化 / 注册
        ↓
获取加密公钥（部分平台）
        ↓
请求发送 OTP（输入手机号）
        ↓
验证 OTP → 获取 Auth Token / Cookie / Session
        ↓
查询 UPI ID（依赖已登录 Token）
        ↓
查询流水列表（依赖已登录 Token，支持分页）
        ↓
查询流水详情（可选）
        ↓
Token 刷新 / 退出登录
```

未携带前置 Cookie 的 OTP 请求会被直接拒绝；未通过 OTP 验证拿到的 Token 则无法访问 UPI ID 与流水接口。这种"逐级解锁"本身就是一种纵深防御。

## 二、OTP 登录接口

OTP（一次性密码）登录是 UPI 钱包的标准身份认证方式，分为**发送**与**验证**两步：

- **Step 1 — 请求发送 OTP：** 客户端提交手机号，服务端向该手机号下发一次性验证码（4~6 位）。
- **Step 2 — 验证 OTP：** 客户端提交验证码，服务端校验通过后返回认证凭证（Token / Cookie），作为后续所有接口的身份标识。

部分平台（如 Paytm）在 OTP 验证后还嵌套一段 **OAuth2 授权流程**（state token → authorization code → access token），最终产出有效期约 **1 个月**的 Bearer Token。

### 2.1 前置步骤

在真正请求 OTP 之前，各平台通常要求一个或多个初始化动作。这意味着"裸请求 OTP"在现代 UPI 钱包中几乎不可能成功：

| 步骤 | 描述 | 典型参数 |
|---|---|---|
| 设备注册 / 配置 | 上报设备信息，换取设备级初始 Token / Session | 设备ID、OS 版本、机型、App 版本 |
| 获取加密公钥 | 拉取 RSA 公钥（有效期约 36 小时），用于后续请求体加密 | 无入参，返回公钥串 + 有效期 |
| 获取初始 Cookie / CSRF Token | 初始化会话上下文 | 通过 `Set-Cookie` 下发 |
| 初始化 Session ID | 创建本次登录会话 | 手机号、设备标识、登录流程类型 |

### 2.2 请求发送 OTP 接口

- **请求方式：** `POST`
- **认证状态：** 匿名（无需登录）

除业务字段外，Header 层携带大量设备与加密标识：

| 参数位置 | 参数名 | 说明 |
|---|---|---|
| Header | `Content-Type` | `application/json` |
| Header | `User-Agent` | 客户端标识（含 App 版本、OS、机型） |
| Header | 设备 ID | 各平台命名不同：`X-Device-ID` / `x-bsy-did` / `x-id` |
| Header | App 版本 | `X-App-Ver` / `x-bsy-appvn` / `x-app-version` |
| Header | 加密公钥 | 部分平台将本次使用的 RSA 公钥置于 Header（如 `pke`） |
| Header | 加密密钥标识 | AES 密钥经 RSA 加密后的密文（如 `cske`），供服务端解密请求体 |
| Header | CSRF Token | 前置步骤获取，防跨站请求 |
| Body | 手机号 | 明文或对称加密后 |
| Body | 设备 ID | 与 Header 一致 |
| Body | 随机标识符 | `nonceToken` / `tid`，用于防重放 |

**成功响应关键字段：**

| 字段名 | 说明 |
|---|---|
| `otpId` / `nid` / `sessionId` | 本次 OTP 的唯一标识，验证时需回传 |
| `otpLength` | OTP 位数（4 或 6） |
| 状态标识 | 各平台不同：`success:true` / `status:"SUCCESS"` |

**常见错误响应：** 手机号不存在或格式错误、请求过于频繁（触发限频）、设备未授权。

### 2.3 验证 OTP 接口

- **请求方式：** `POST`
- **认证状态：** 匿名

客户端回传用户输入的 4~6 位验证码，以及发送阶段返回的 `otpId` / `sessionId` / `nonceToken` 等关联标识。验证通过后服务端下发**认证凭证**——而凭证的具体形态，是各平台差异最大的地方：

| Token 形态 | 说明 | 典型平台 |
|---|---|---|
| HTTP Cookie（如 `app_fc`） | 存于 `Set-Cookie`，后续自动携带 | FreeCharge |
| Header 字段拼接 | `hashid + "." + token` 组合为 `Authorization` | MobiKwik |
| Body 中的 `accessToken` | Bearer Token，需手动注入 `Authorization` Header | Paytm、PhonePe |
| 多字段 Session Cookie | `session-token`、`at-acbin` 等共同维持会话 | Amazon Pay |
| 动态 + 静态双 Token | 动态 Token 每请求刷新，静态 Token 长期持有 | Airtel |

**OTP 验证失败常见情形：**
- OTP 错误（剩余尝试次数递减）
- OTP 过期（通常有效期约 **3~5 分钟**）
- 超过最大尝试次数（通常 **5 次后锁定 24 小时**）

## 三、加密体系

UPI 钱包普遍采用 **RSA + AES 混合加密** 模式，兼顾安全与性能：

- **非对称层（RSA）：** 客户端拉取服务端 RSA 公钥（有效期约 36 小时），用于加密一次性 AES 密钥。
- **对称层（AES）：** 真正的业务请求体（如手机号）用 AES 加密；AES 密钥本身经 RSA 公钥加密后放入 Header（`cske`）一并发送，供服务端用私钥还原。

这与 TLS 之内再套一层应用层加密的"双层防护"思路一致：即便传输层被中间人观察（例如抓包代理），应用层密文仍能保护敏感字段。

此外，三类辅助标识各司其职：

| 标识 | 职责 |
|---|---|
| `nonceToken` / `tid` | **防重放**——同一请求不可二次提交 |
| CSRF Token | **防跨站**请求伪造 |
| 设备指纹（设备ID / 机型 / OS / App 版本） | **设备绑定与风控** |

## 四、查询 UPI ID 与交易流水

拿到认证凭证后，两条核心业务链路被打开：

1. **查询 UPI ID（VPA）：** 依赖已登录 Token，返回用户注册的虚拟支付地址（如 `xxxx@bank`）及绑定状态。部分平台会在 OTP 验证响应中直接附带该信息。
2. **查询流水：** 同样依赖 Token，支持分页拉取交易列表，并可进一步查询单笔详情。

这两类接口直接暴露用户资金轨迹，是 UPI 钱包风控与隐私保护的焦点，通常叠加额外的设备校验与频率限制。

## 五、安全机制小结

纵观整套通用协议，UPI 钱包的安全设计可归纳为五道防线：

| 防线 | 机制 |
|---|---|
| 传输安全 | HTTPS / TLS，部分 HTTP/2 |
| 应用层加密 | RSA + AES 混合，公钥短期轮换（约 36h） |
| 身份认证 | OTP 两步验证 + 多步 OAuth（Paytm） |
| 会话绑定 | 设备指纹、CSRF、Session ID |
| 风控限频 | OTP 限频、尝试次数锁定（5 次 / 24h）、防重放 nonce |

## 六、方法论小结

UPI 钱包类 App 在功能上看似简单，其通信协议却是一套 **强状态依赖 + 多层加密 + 多形态凭证** 的复合体系。各平台在 Token 形态、前置步骤、加密细节上各有取舍，但底层模型高度一致——这正是"通用协议"得以抽象的基础。

逆向分析此类 App 的推荐路径：

1. **先建立会话上下文**：抓包时务必从冷启动开始，完整记录设备注册 → 公钥拉取 → Cookie 获取的前置链路，否则后续请求无法复现。
2. **识别加密层**：定位客户端内的 RSA 公钥缓存与 AES 密钥生成逻辑，通常集中在网络层或独立的 crypto 类。
3. **跟踪 Token 生命周期**：注意区分短期 Token 与长期 Token，以及它们在 Header / Cookie / Body 中的不同注入位置。
4. **关注风控信号**：限频、尝试次数锁定、设备指纹校验是协议之外的"隐性约束"，往往决定自动化方案的可行性边界。

理解这套模型，对于 **移动支付安全研究、客户端逆向分析、风控规则建设** 都具有直接的参考价值。
